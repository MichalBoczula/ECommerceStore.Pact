# ECommerceStore.Pact

Versioned contract artifacts and compatibility history for the ECommerceStore applications.
The delivery plan is in [TECHNICAL_TODO.md](TECHNICAL_TODO.md).

## Current implementation: PACT/01-06 and PACT/07 release configuration

ASP.NET Core 10 Minimal API, MongoDB configuration and bounded readiness checks,
generated OpenAPI, ProblemDetails, local Compose and a GitHub Actions quality gate.
Immutable application versions and directed consumer/provider integrations can now be
registered and read from MongoDB. Immutable OpenAPI/Pact artifacts and publication provenance
are stored separately and downloaded byte-for-byte. Provider CI can append immutable verification
reports with structured diagnostics and retrieve their history. Explicit publication comparisons
and evidence-based issue transitions are available. Compatibility decisions now evaluate exact
version pairs and CI executions against a pinned required-check profile;
an accepted contract upload is not a passing test.

| Endpoint | Behavior |
| --- | --- |
| `GET /health/live` | 200 when the process serves requests; does not contact MongoDB. |
| `GET /health/ready` | 200 when MongoDB responds to ping, otherwise 503. |
| `GET /openapi/v1.json` | OpenAPI generated by the application. |
| `POST /api/applications/{applicationId}/versions` | Register by full commit SHA; 201 new, 200 equivalent retry, 409 conflicting metadata. |
| `GET /api/applications/{applicationId}/versions/{commitSha}` | Read the exact registered version; 404 if absent. |
| `POST /api/integrations` | Declare a directed consumer/provider pair; 201 new, 200 equivalent retry. |
| `GET /api/integrations/{consumerApplicationId}/{providerApplicationId}` | Read a declared integration; 404 if absent. |
| `POST /api/contract-publications` | Publish a contract with registered source version and build provenance; 201 new, 200 retry, 409 conflicting content. |
| `GET /api/contract-publications/{id}` | Read a publication and its source/integration/artifact references. |
| `GET /api/artifacts/{sha256}` | Read immutable artifact metadata. |
| `GET /api/artifacts/{sha256}/content` | Download original bytes, with hash ETag and attachment filename. |
| `POST /api/verification-runs` | Append a provider CI report; 201 new execution, 200 equivalent retry, 409 changed report for the same execution. |
| `GET /api/verification-runs/{id}` | Read the original report and diagnostics. |
| `GET /api/verification-runs?consumerApplicationId=...&providerApplicationId=...&contractSha256=...` | Bounded history for an explicit integration and Pact hash; optional `limit` (1-100) and `after` cursor. |
| `POST /api/contract-comparisons` | Snapshot explicit before/after publications within an integration and selected branch baseline; 201 new, 200 retry. |
| `GET /api/contract-comparisons/{id}` | Read an immutable comparison snapshot. |
| `GET /api/issue-history?beforeRunId=...&afterRunId=...&baselineRef=refs/heads/main` | Compare explicit verification evidence and project issue transitions. |
| `POST /api/verification-profiles` | Register consumer-owned required checks by integration/name/version; 201 new, 200 equivalent retry, 409 changed checks. |
| `GET /api/verification-profiles/{id}` | Read an immutable required-check profile. |
| `POST /api/compatibility-decisions` | Evaluate and snapshot up to 10 explicit version pairs under a pinned profile; 201 new evidence snapshot, 200 equivalent retry. |
| `GET /api/compatibility-decisions/{id}` | Read the original decision, profile/policy, outcomes and supporting evidence. |

Health responses expose dependency statuses, never connection strings or driver
exceptions. Unmatched routes return `application/problem+json` with a `traceId`.
Missing or invalid MongoDB configuration prevents startup; an unavailable database
does not prevent startup, but keeps readiness unhealthy.

Registration uses unique indexes and insert-only atomic upserts. Records retain their
original IDs and timestamps under retries/concurrency. An integration declaration does
not mean that its contract passed verification. All POSTs now require a Bearer publisher token
authorized for the target application (integration declarations are owned by their consumer).
Public reads and health require no credentials. Empty publisher configuration denies all writes.

## Payments consumer pilot (PACT/08)

[Payments PR #49](https://github.com/MichalBoczula/ECommerceStorePayments/pull/49) adds five
consumer-owned Pact HTTP interactions through the production Kiota, precise-parser and mapping
boundary. Its required ExternalProviders job exports reproducible spec-v4 JSON and a SHA-256
manifest. No registry deployment is required. See the [pilot guide](docs/payments-consumer-pilot.md)

## Register a version and integration

```bash
. ./.env
curl -i http://localhost:5080/api/applications/payments/versions \
  -H "Authorization: Bearer $PACT_PUBLISHER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"commitSha":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","repositoryUrl":"https://github.com/MichalBoczula/ECommerceStorePayments"}'
curl -i http://localhost:5080/api/integrations \
  -H "Authorization: Bearer $PACT_PUBLISHER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"consumerApplicationId":"payments","providerApplicationId":"invoice"}'
```

Use the actual full commit SHA in CI. IDs and SHAs are normalized to lowercase; repository
URLs use HTTPS without credentials/query/fragment. An optional `imageDigest` must have the
form `sha256:<64 hex characters>`. Version metadata is fixed at registration, including
an omitted digest. Branch/ref is publication metadata (PACT/03), not a version field.
Unknown request properties are rejected. See [ADR-0001](docs/adr/0001-registration-identities.md).

## Publish contracts

`POST /api/contract-publications` accepts this JSON envelope (replace the content placeholder
with base64 of the original file bytes):

```json
{
  "sourceApplicationId": "payments",
  "commitSha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "kind": "ConsumerPact",
  "consumerApplicationId": "payments",
  "providerApplicationId": "invoice",
  "sourceRef": "refs/heads/main",
  "buildUrl": "https://github.com/MichalBoczula/ECommerceStorePayments/actions/runs/1",
  "contentBase64": "<base64 of original UTF-8 Pact JSON>"
}
```

Register the source version and consumer/provider integration first. For `ProviderOpenApi`,
the source application is the provider and the consumer/provider fields must be omitted.
Supported profiles are OpenAPI 3.0/3.1 JSON and Pact 3/4 HTTP with matching logical party names;
messages, plugins, external OpenAPI references and duplicate JSON property names are rejected.
The original artifact is limited to 1 MiB; the complete upload envelope to 2 MiB, also when
Content-Length is unknown. Limits return 413; bad profiles return 400; missing references 404.

Identical bytes share a hash across application versions. An immutable version/kind/integration
binding cannot change bytes, even on another branch. Each branch/build/publisher combination
has its own publication identity and timestamp. See [ADR-0002](docs/adr/0002-contract-publication.md).

Publisher tokens are configured under `RegistryAuth:Publishers:<publisher-id>` with `TokenSha256`
and an `ApplicationIds` array, e.g. `payments` for that service's CI. The local bootstrap credential
uses `*` to manage the local demo. Publisher ID comes from authentication, not the request body.
Use secret injection for token hashes in deployed configuration; keep bearer tokens in CI secrets.

## Ingest verification reports

Provider CI executes official Pact tooling and posts a normalized report using a token scoped
to the **provider** application. Register both versions and publish the consumer Pact first.
The registry validates references, coverage counts and diagnostics; it trusts authorized CI's
reported execution. Real source-repository verifier integration is PACT/08-09.

Example `POST /api/verification-runs` (replace publication ID, commits, hashes and tool version
with the exact values used by CI):

```json
{
  "consumerPublicationId": "11111111-1111-1111-1111-111111111111",
  "consumerApplicationId": "payments",
  "consumerCommitSha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "providerApplicationId": "invoice",
  "providerCommitSha": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "contractSha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
  "verifierName": "pact-core",
  "verifierVersion": "<exact installed version>",
  "configurationSha256": "dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd",
  "ciRunId": "123",
  "ciAttempt": 1,
  "ciCheckId": "pact/orders",
  "sourceRef": "refs/heads/main",
  "buildUrl": "https://github.com/MichalBoczula/ECommerceStoreInvoice/actions/runs/123",
  "status": "Failed",
  "verifiedInteractions": 0,
  "failedInteractions": 1,
  "summary": "Missing required response field",
  "issues": [{
    "kind": "Mismatch",
    "code": "missing_body_field",
    "message": "Expected totalAmount",
    "interaction": "read an order",
    "method": "GET",
    "path": "/orders/123",
    "jsonPath": "$.body.totalAmount",
    "expected": 12.34,
    "actualPresent": false
  }],
  "evidenceUrls": [],
  "startedAt": "2026-01-01T00:00:00Z",
  "finishedAt": "2026-01-01T00:00:01Z"
}
```

`verifiedInteractions` counts successful interactions; `failedInteractions` counts mismatched
interactions. The registry derives `expectedInteractions` from the immutable Pact. Passed
requires complete success and no issues. Failed requires mismatch diagnostics. Error requires
an `ExecutionError` issue and can preserve partial mismatches. Unverified requires zero completed
interactions, no issues and a summary explaining why execution was not attempted.

A mismatch includes the Pact interaction description, HTTP operation, JSON path, expected JSON
value and `actualPresent`. For a missing value, use false and omit `actual`; for explicit JSON
null, use true and `"actual": null`. JSON numbers retain precision. Evidence URLs use HTTPS
without credentials or query parameters; log fragments are allowed. Do not publish secrets in
reports; reads are public. The complete report is limited to 1 MiB, with at most 100 issues,
10 evidence URLs and 8 KiB per expected/actual JSON value.

The same CI run + attempt + check for a version pair/binding/hash is retry-stable. A changed
report returns 409. A new run, attempt or check records another execution without replacing
history. Supply fixed original execution timestamps when retrying; do not regenerate them.
History pages use ascending record IDs, not time or compatibility priority; `nextCursor` is
passed as `after`. With concurrent inserts, restart traversal to include earlier-sorted new IDs.
See [ADR-0003](docs/adr/0003-verification-runs.md) for identities and status rules.

## Compare contracts and issue history

`POST /api/contract-comparisons` requires a publisher token scoped to `sourceApplicationId`:

```json
{
  "sourceApplicationId": "invoice",
  "consumerApplicationId": "payments",
  "providerApplicationId": "invoice",
  "beforePublicationId": "11111111-1111-1111-1111-111111111111",
  "afterPublicationId": "22222222-2222-2222-2222-222222222222",
  "baselineRef": "refs/heads/main"
}
```

Select two existing publications of the same kind and source application. Provider OpenAPI
belongs to the selected integration's provider; consumer Pact belongs to its consumer.
The integration must be registered. `baselineRef` must match the **before publication's** ref;
the candidate may come from a feature branch. There is no automatic latest baseline. Environment
selection requires future deployment records; compatibility currently targets explicit commits. Comparison requests use the same streamed 1 MiB
JSON envelope limit as verification reports.

Results separate `contentChanged` (exact bytes), `jsonChanged` (structural JSON, retaining array
order/number spellings), `schemaAssessment` and `consumerImpact`. OpenAPI analysis uses pinned
**oasdiff 1.35.0** with external references disabled. Additive optional response fields have no
breaking finding; required response-field removal is identified. `NoBreakingChangesDetected`
is limited to the documented tool/profile, not proof that a consumer passes. `consumerImpact`
is always `NotEvaluated` on a schema/content comparison. Consumer Pact gets structural content
comparison with `NotAssessed` schema status; it is never converted into provider-generated expectations.

Comparisons are immutable snapshots keyed by integration/publications/ref/profile. Retry preserves
original ID, publisher, time and findings, including when the tool later becomes unavailable.
Tool/version/timeout/output errors return 503 and do not store an empty safe result. No update/delete
endpoint exists. See [ADR-0004](docs/adr/0004-contract-changes-and-issue-history.md) for supported
requiredness/type/nullability/reference/composition semantics and conservative limitations.

Issue history is a read-only projection of **two selected verification runs**. Pass their IDs
and the before run's provider ref to `/api/issue-history`. The response includes both original
reports, diagnostics/evidence and a versioned transition policy. The same issue is identified
by integration, code, interaction, method/path, JSON path and expected JSON; actual values and
message wording may vary.

- `Appeared`: baseline Passed, candidate now reports the mismatch.
- `Persisting`: both runs report the same requirement failing.
- `Resolved`: candidate Passed against the exact same Pact hash, verifier/version/configuration and check.
- `Unconfirmed`: an old issue is absent, but the candidate did not pass (including Error/Unverified).
- `RequirementsChanged` / `VerifierChanged`: runs cannot prove a fix under this policy.
- `Observed`: a candidate mismatch is present without a comparable passing baseline.

Removing a consumer requirement never becomes a provider fix. Even byte-only changes to a Pact
are conservative `RequirementsChanged` under this exact-hash policy. These projections never
change the original Failed/Error evidence. Full timeline/report filtering is PACT/11.

## Decide compatibility for explicit versions

The consumer first registers an immutable profile of **all required checks** using a token
scoped to the consumer application. For example, POST `/api/verification-profiles`:

```json
{
  "consumerApplicationId": "payments",
  "providerApplicationId": "invoice",
  "name": "required-pact",
  "version": "1",
  "checks": [{
    "checkId": "pact/orders",
    "verifierName": "pact-core",
    "verifierVersion": "<exact installed version>",
    "configurationSha256": "dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd"
  }]
}
```

Profiles require 1-10 distinct check IDs. Integration/name/version identifies immutable content;
changing checks returns 409 and requires a new profile version. Check order is irrelevant.
Pin the returned profile ID in source CI configuration; do not discover an arbitrary or latest
profile at release time. The registry enforces that chosen profile's complete check set. Reviewing
whether that set covers the application's business requirements remains part of consumer CI.

Either side may request a decision using a token scoped to its `sourceApplicationId`:

```json
{
  "sourceApplicationId": "invoice",
  "profileId": "11111111-1111-1111-1111-111111111111",
  "rows": [{
    "consumerCommitSha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "providerCommitSha": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
    "contractSha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
    "ciRunId": "123",
    "ciAttempt": 1,
    "providerSourceRef": "refs/heads/main"
  }]
}
```

POST `/api/compatibility-decisions` resolves registered versions and that consumer version's
integration binding. Select 1-10 distinct rows; each can use its own CI run/attempt. The exact
hash must match an existing binding. A missing binding gives Unverified/ContractNotPublished;
a missing selected check gives Unverified/MissingExecution. Wrong verifier/version/configuration
or provider ref is Unverified with the observed report retained for diagnosis. Another commit,
run, attempt, check, consumer version or Pact hash cannot supply the missing evidence.

The `explicit-ci-execution-v1` policy requires every profile check to be applicable and Passed.
Row and matrix aggregation uses **Failed > Error > Unverified > Passed**. `compatible` is true
only for Passed and is scoped to the requested pairs/profile. Schema equality and schema
comparisons do not participate. Results include per-check reasons, missing/unresolved check IDs,
observed status/verifier, evidence IDs/URLs, original publication, payload hash and CI provenance.
Follow each evidence URL for the complete immutable report and diagnostics.

Equivalent observed evidence returns the same decision ID/time/publisher (200), even with
reordered rows or another authorized requesting credential. Newly available selected evidence
creates a new snapshot (201), preserving old Unverified/Failed decisions. A later passing rerun
must be selected explicitly; it cannot overwrite an earlier failed attempt. GET by decision ID
returns the stored policy, profile, row/matrix outcomes and evidence without reevaluation.

Each request uses a streamed 1 MiB UTF-8 JSON envelope. Unknown/duplicate properties and empty,
duplicate or oversized selections return 400; missing registered references return 404; storage
outage returns 503. These decisions target full commit SHAs. Environment selectors and deployment
records are not implemented; `compatible` does not assert that every deployed dependency was
included. Official Pact execution/source CI gates remain PACT/08-09. See
[ADR-0005](docs/adr/0005-explicit-compatibility-decisions.md).

## Run locally

Requires Docker with Compose:

```bash
bash scripts/init-local.sh
docker compose up --build -d
curl http://localhost:5080/health/ready
curl http://localhost:5080/openapi/v1.json
docker compose down
```

The local-only stack binds API and MongoDB ports to loopback. MongoDB data is in
the `pact-mongodb` volume; `docker compose down --volumes` removes that local data.
Set `PACT_HTTP_PORT` or `PACT_MONGO_PORT` when the default ports are occupied.

For host execution/tests, install Go 1.27.3, then build the pinned comparison binary (Linux amd64/arm64):

```bash
sh scripts/install-oasdiff.sh "$PWD/artifacts/tools"
export OASDIFF_PATH="$PWD/artifacts/tools/oasdiff"
```

The installer verifies the committed source archive SHA-256 and enforces the Go toolchain pin.
It rebuilds unmodified oasdiff 1.35.0 source with Go 1.27.3 because the upstream release binary
contains a vulnerable Go standard library (CVE-2026-111943). Go modules remain locked by the
upstream go.mod/go.sum. On Windows/macOS, build the same source with the patched toolchain and
upstream version linker flag, then set `OASDIFF_PATH`. `Comparison__Executable` can also select
its absolute path. The API checks the executable's version before analysis. Docker/CI build it
automatically; unavailable comparison tooling does not prevent health or registry reads/writes.

To run the API on the host with .NET SDK 10:

```bash
docker compose up mongodb -d
. ./.env
RegistryAuth__Publishers__local__TokenSha256="$PACT_PUBLISHER_TOKEN_SHA256" \
RegistryAuth__Publishers__local__ApplicationIds__0='*' \
  dotnet run --project src/ECommerceStore.Pact.Api --launch-profile http
```

Development settings use `mongodb://localhost:27017`. Outside Development, set
`Mongo__ConnectionString` explicitly. Other settings are `Mongo__DatabaseName`
(default `ecommercestore-pact`) and `Mongo__TimeoutSeconds` (1-30, default 3).
The connection string is never committed with deployment credentials.

## Verification

```bash
bash scripts/verify.sh
```

The same scripts run in CI: locked restore with high/critical NuGet audit failures,
source/architecture checks, formatting, build, Domain/Application/Infrastructure/HTTP
tests, real MongoDB concurrency/index/publication tests and an authenticated Docker Compose
smoke covering immutable publication, exact-byte content retrieval, synthetic report ingestion,
real pinned-tool comparison, evidence-based issue history and explicit-version compatibility decisions.
Reports are under `artifacts/`. The integration fixture starts
MongoDB 8 through Testcontainers. Alternatively, set `PACT_TEST_MONGODB` to a local
test MongoDB connection; this does not skip the actual database check.

Container CI builds one Linux/amd64 candidate, runs the full Compose smoke against it, and
scans fixed HIGH/CRITICAL vulnerabilities with Trivy. On a successful main push, a separate
job loads that same tested image archive and publishes it to Docker Hub after the quality
gate. PR/dispatch checks need no registry credentials. See [deployment instructions](docs/deployment.md)
for required push secrets, the immutable image receipt and the companion shared Azure Terraform
configuration. Actual publication/apply/hosted readiness still need operator configuration.

## Image publication and Azure

Set `DOCKER_USER` and `DOCKER_TOKEN` repository secrets for the Pact image's Docker Hub account.
Existing `DOCKERHUB_USERNAME` / `DOCKERHUB_TOKEN` names are accepted as fallbacks. Optional
`DOCKER_IMAGE` selects a namespace/repository (default `mb0101/ecommerce-store-pact-api`).
A main push fails publication with a named missing-setting error when credentials are absent;
it never silently claims to have published an image.

The `pact-image-reference` workflow artifact contains `image-reference.json` with the verified
source commit, local image ID and registry digest. Deploy its `imageReference` field through
`app_images.pact` in [ECommerceStore.Terraform](https://github.com/MichalBoczula/ECommerceStore.Terraform),
using the existing ACA environment/state/Mongo cluster, a dedicated database and scoped publisher
hashes injected through ACA secret references. Terraform does not create another cluster or
an environment for this registry. Configuration is opt-in and the hosted image must use a digest.

After an operator applies the reviewed Terraform plan, verify readiness and publisher scope:

```bash
# Supply the existing raw publisher token through the environment, not a URL or argument.
python3 scripts/verify-deployment.py --url https://YOUR-PACT-HOST --application payments
```

Set `PACT_PUBLISHER_TOKEN` securely before running the command. It checks Mongo readiness,
liveness and anonymous-write rejection, then verifies the scoped credential using a deliberately
invalid repository URL that fails before persistence. It writes no registry records and refuses
redirects. Full operator instructions and rollout limits are in [docs/deployment.md](docs/deployment.md).

## Planned application boundaries

Consumer tests execute each application's real adapter and generated Kiota client
against Pact's mock provider. Provider verification executes the resulting Pact
against an actual provider API. CI publishes immutable artifacts and verification
evidence here. The registry determines a decision for explicit application versions;
it does not infer runtime compatibility from a schema diff alone.

The initial pilot is Payments -> Invoice. The remaining integration inventory,
including BFF registration, is in [docs/integrations.md](docs/integrations.md).
See [docs/architecture.md](docs/architecture.md) for the intended data model and
version-selection rules.
